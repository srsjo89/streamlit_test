# 데이터사업팀 지식 위키 — 작성 규칙서 (v1.2)

이 문서는 위키를 관리하는 AI 에이전트가 따르는 규칙서다.
`raw/`의 원본(인수인계 녹취, 품의서, 회의록 등)을 읽고, `wiki/`에 서로 연결된 마크다운 페이지를 만들고 갱신한다.
페이지 형식은 OKF(Open Knowledge Format) 방식을 따른다. 폴더 안의 마크다운 파일 + 맨 위 라벨(frontmatter) + 서로 간 링크.

---

## 0. 이 위키의 목적

- **1차 목적**: 신규 입사자(조윤성)가 인수인계받은 내용을 빠짐없이 기록하고, 팀 업무의 전체 지도를 만든다.
- **장기 목적**: 팀의 사업 이력·절차·규정·노하우를 공유 지식으로 쌓아, 담당자가 아니어도 과거 사례를 찾아 쓸 수 있게 한다.
- **독자**: 데이터사업팀 구성원. 영업 담당자와 분석·처리 담당자 모두.

**핵심 원칙: 요약하지 말고 보존한다.** 인수인계의 가치는 세부 절차, 숫자, 예외, "왜 그렇게 하는지"에 있다. 짧게 줄이느라 이것들을 잃으면 안 된다.

## 1. 폴더 구조

```
raw/                  ← 원본. 에이전트는 읽기만 한다. 절대 수정·삭제 금지
wiki/
  index.md            ← 전체 목차
  log.md              ← 작업 일지
  확인필요.md          ← 동료에게 물어볼 질문 모음
  업무/               ← 팀이 하는 업무 영역
  사업/               ← 개별 사업·계약 건
  프로세스/           ← 단계가 있는 절차
  규칙/               ← 반드시 지킬 것, 하면 안 되는 것, 노하우
  시스템/             ← 사내 시스템, 도구
  용어/               ← 개념, 약어, 사내 용어
  기관/               ← 고객사, 대행사, 평가기관, 협력사
  사람/               ← 담당자 맵 (업무 연락 목적만)
  조직/               ← 사내 팀·부서
  출처/               ← 원본 파일 하나당 한 장의 안내 페이지
```

**파일명 규칙**
- 페이지 제목을 파일명으로 쓴다. 공백은 하이픈(`-`)으로 바꾼다.
  예: `wiki/규칙/외부발송-용량과-파일분할.md`
- 링크는 파일명(확장자 제외)으로 건다: `[[외부발송-용량과-파일분할]]`
- 원본 파일명 권장 형식: `YYYY-MM-DD_설명자_주제.txt` (예: `2026-09-28_서선화_데이터제공프로세스.txt`)

## 2. 페이지 종류와 쓰임

| type | 무엇을 담나 | 예시 |
|---|---|---|
| 업무 | 팀의 업무 영역 하나. 배경, 규모, 담당, 관련 프로세스 | LMS 광고, 데이터 외부 제공, 데이터 전문기관, 데이터 전송 개발 |
| 사업 | 특정 고객·기관과의 개별 사업 또는 계약 | 신세계 가명정보 제공, 이마트24 정기 결합 |
| 프로세스 | 순서가 있는 절차. 단계, 담당, 소요기간, 산출물 | 데이터 외부 제공 전체 프로세스, 적정성 평가, 가명·익명 시스템 DB 접근 신청 |
| 규칙 | 지켜야 할 것 / 하면 안 되는 것 / 경험에서 나온 노하우 | 전결 확인, 외부발송 용량과 파일분할, CB는 다른 회사로 간주 |
| 시스템 | 사내 시스템·도구. 용도, 접속 방법, 권한, 주의점 | 가명·익명 시스템, DLS |
| 용어 | 개념 정의, 사내 용어, 약어 | 가명정보, 익명정보, 추진품의, 이행확약서 |
| 기관 | 외부 조직 | 금융보안원, 바나나몽키스, 나이스 |
| 사람 | 누가 무엇을 담당하고 무엇을 물어보면 되는지 | 담당자별 페이지 |
| 조직 | 사내 팀·부서. 구성원, 하는 일, 우리 팀과의 관계 | 데이터사업팀, 데이터솔루션팀 |
| 출처 | 원본 파일 하나의 안내: 언제, 누가, 무엇을 다뤘나 | 서선화-OJT-2026-09-28 |

**새 type을 임의로 만들지 않는다.** 어디에도 맞지 않으면 가장 가까운 type에 넣고 `확인필요.md`에 "type 추가 검토"로 남긴다.

## 3. 라벨(frontmatter) 규칙

모든 페이지 맨 위에 `---`로 감싼 라벨을 붙인다.

### 3-1. 공통 필드 (모든 페이지 필수)

```yaml
---
type: 규칙                     # 2장의 type 중 하나
title: 외부발송 용량과 파일분할   # 사람이 읽는 제목
aliases: [외부 문서 발송 용량, 파일 쪼개기]   # 같은 대상을 부르는 다른 이름들
status: 초안                   # 초안 | 검수완료 | 폐기
stale_after: 2027-09-28        # 이 날짜 이후엔 재확인 필요 (4장 참고)
sources:                       # 근거가 된 원본과 위치
  - raw/2026-09-28_서선화_데이터제공프로세스.txt#09:09
updated: 2026-09-28
---
```

### 3-2. type별 추가 필드

| type | 추가 필드 |
|---|---|
| 업무 | `담당: [[사람]]`, `관련프로세스: [[...]]`, `관련기관: [[...]]` |
| 사업 | `기관: [[...]]`, `업무: [[...]]`, `제공분류: 가명·가명결합·익명·기타 중`, `주기: 단건·월·분기·반기·연`, `상태: 진행중·종료·예정` |
| 프로세스 | `업무: [[...]]`, `선행: [[...]]`, `후속: [[...]]`, `소요기간: "발언 그대로"` |
| 규칙 | `적용대상: [[프로세스 또는 업무]]`, `중요도: 필수·권장·참고` |
| 시스템 | `용도: "한 줄"`, `관련프로세스: [[...]]` |
| 용어 | `분야: 개인정보·결재·데이터처리·영업·기타` |
| 기관 | `기관유형: 고객사·대행사·평가기관·규제기관·협력사·경쟁사` , `관련업무: [[...]]` |
| 사람 | `소속: [[조직]]`, `직책: 팀장·파트장·프로`, `파트: "..."`, `담당업무: [[...]]`, `담당기관: [[...]]` |
| 조직 | `조직유형: 우리팀·협업팀·타부서`, `팀장: "이름"` (사람 페이지가 있으면 [[링크]]) |
| 출처 | `날짜`, `길이`, `설명자: [[사람]]`, `원본: raw/...` |

**값을 모르면 필드를 비워두지 말고 `확인필요`라고 쓴다.**

### 3-3. 통제어휘 (정해진 값만 사용)

- **제공분류**: `가명` / `가명결합` / `익명` / `기타` — 통계는 `기타`에 포함된다 (서선화 설명 기준).
- **status**: `초안` / `검수완료` / `폐기`
- **기관유형**, **주기**, **중요도**, **분야**: 위 표의 값만 사용.
- 목록에 없는 값이 필요하면 가장 가까운 값을 쓰고 `확인필요.md`에 추가 제안을 남긴다.

## 4. status와 stale_after 규칙

### status (진행 상태)
- 에이전트가 만들거나 고친 페이지는 항상 `초안`이다.
- **`검수완료`로 바꾸는 것은 사람만 한다.** 에이전트는 절대 `검수완료`로 설정하지 않는다.
- `검수완료` 페이지의 내용을 에이전트가 실질적으로 바꾸면, status를 `초안`으로 되돌리고 `log.md`에 "검수완료 → 초안 (사유)"를 남긴다. 오타·링크 수정은 예외.

### stale_after (유통기한) 기본값
| 내용 | 기본 유통기한 |
|---|---|
| 목표·실적 등 연도가 붙은 숫자 | 그 연도의 12월 31일 |
| 사람의 담당 업무, 담당 기관 | 작성일 + 6개월 |
| 프로세스, 시스템 사용법 | 작성일 + 1년 |
| 규칙·규정 | 작성일 + 1년 |
| 개념 용어, 히스토리 | `없음` |
| 사업 | 계약 종료일 (모르면 작성일 + 1년) |

## 5. 본문 양식

### 5-1. 모든 페이지 공통
- 첫 줄에 `# 제목`
- 바로 아래 **한 줄 요약** (이 페이지가 무엇인지)
- 마지막에 `## 관련` 섹션: 연결된 페이지 링크 목록
- 사실마다 근거를 남긴다: 문장 끝에 `(출처: 서선화 09:09)` 형식

### 5-2. type별 섹션

**업무**
```
## 개요 / ## 배경과 히스토리 / ## 규모와 숫자 / ## 담당과 역할 분담
## 주요 프로세스 / ## 주의사항·리스크 / ## 관련
```

**사업**
```
## 개요 / ## 수요 배경 / ## 제공 데이터와 수준 / ## 계약·금액
## 이력(회차별) / ## 쟁점과 결정 / ## 관련
```

**프로세스**
```
## 개요
## 단계
| 순서 | 단계 | 담당 | 산출물·결재 | 소요기간 | 주의 |
## 예외와 변형 (분류별·상황별로 달라지는 부분)
## 자주 하는 실수
## 관련
```

**규칙**
```
## 규칙 (한 문장, "~한다" / "~하지 않는다")
## 이유 (왜 이 규칙이 있나)
## 어기면 생기는 일
## 구체적인 방법
## 관련
```

**시스템**
```
## 용도 / ## 접속과 권한 신청 / ## 주요 기능 / ## 실제 사용 방식(공식 기능과 다르면 명시)
## 주의점 / ## 관련
```

**용어**
```
## 정의 / ## 헷갈리는 점 (비슷한 용어와의 차이) / ## 사용 예 / ## 관련
```

**기관**
```
## 개요 / ## 우리와의 관계 / ## 거래·협업 이력 / ## 담당자(우리 쪽) / ## 관련
```

**사람**
```
## 담당 / ## 이런 걸 물어보면 된다 / ## 관련
```

**조직**
```
## 개요 / ## 구성원 / ## 하는 일 / ## 우리 팀과의 관계 / ## 관련
```

**출처**
```
## 메타 (날짜, 길이, 설명자, 청취자)
## 다룬 주제 (타임스탬프와 함께, 각 주제가 반영된 페이지 링크)
## 이 원본에서 생긴 확인필요 항목
```

## 6. 넣기(ingest) 절차

**한 번에 원본 파일 하나씩** 처리한다.

1. **원본 전체를 끝까지 읽는다.** 중간만 읽고 쓰지 않는다.
2. **STT 오인식을 교정한다.** 7장의 교정 사전을 적용하고, **사람 이름은 7-1 명단과 먼저 대조한다.** 사전에 없는데 오인식이 의심되면 `교정어(원문: ○○)` 형태로 병기하고 `[확인필요]`를 붙인다.
3. **출처 페이지를 먼저 만든다.** 다룬 주제를 타임스탬프와 함께 목록화한다.
4. **대상 목록을 뽑는다.** 이 원본에 나온 업무, 사업, 프로세스, 규칙, 시스템, 용어, 기관, 사람 후보를 나열한다.
5. **기존 페이지와 대조한다.** `index.md`와 각 페이지의 `aliases`를 확인해, 이미 있는 대상이면 **새로 만들지 않고 기존 페이지에 추가**한다. 같은 대상인지 확신이 없으면 새로 만들되 `확인필요.md`에 "○○와 △△가 같은 대상인지"를 남긴다.
6. **페이지를 만들고 갱신한다.**
   - 한 페이지에는 한 주제만.
   - 프로세스 안의 한 단계가 따로 자주 언급되거나 자체 절차가 있으면 별도 프로세스 페이지로 분리하고 링크한다. (예: 적정성 평가)
   - 기존 내용과 새 내용이 다르면 지우지 말고 8장의 상충 표시를 한다.
7. **링크를 양방향으로 건다.** A 페이지에서 B를 링크했으면 B의 `## 관련`에도 A를 추가한다.
8. **index.md, log.md, 확인필요.md를 갱신한다.**
9. **보고한다.** 작업이 끝나면 다음을 보고한다.
   - 새로 만든 페이지 / 갱신한 페이지 목록
   - 추가된 확인필요 항목
   - 교정 사전에 추가할 것을 제안하는 항목
   - 규칙서 자체에서 불편했던 점 (있으면)

## 7. STT 교정 사전

녹취 변환(클로바노트 등)에서 반복되는 오인식. 확신도가 `추정`인 항목은 페이지에 쓸 때 첫 등장 시 `[확인필요]`를 붙인다.

| 녹취 표기 | 교정 | 확신도 |
|---|---|---|
| 감염, 감명, 감형, 가형, 감면, 암명 | 가명 | 높음 (문맥상 개인정보 처리일 때) |
| 인명, 입면, 이명 | 익명 | 높음 (문맥상 개인정보 처리일 때) |
| 가익명, 가입명, 가입 내역 | 가·익명 | 높음 |
| 품위, 푸 | 품의 | 높음 |
| 추징품위, 출입품위, 추진품이 | 추진품의 | 높음 |
| 시소, c소 | CISO(정보보호최고책임자) | 높음 |
| 금보원, 근본원, 금버거, 금봉 | 금융보안원 | 높음 |
| cb, CD (신용정보 문맥) | CB(신용평가회사) | 높음 |
| 결합기 | 결합키 | 높음 |
| 해지 (파일 비교 문맥) | 해시 | 높음 |
| 셀업 | 셋업 | 높음 |
| 정류 분류 | 정보 분류 | 높음 |
| 오제이트 | OJT | 높음 |
| 바나나 모키스, 바나나 노기스, 바나나 몽키스 | 바나나몽키스 | 높음 |
| 에드 탱크, 애드 탱크 | 애드탱크 | 높음 |
| 14년도 (LMS 문맥) | 24년도 | 높음 (발언자 본인 정정) |
| 경지, 경제 (품의 합의 문맥) | 경영지원 부서 | 높음 (확인됨) |
| 방송, 방송용 (권한 삭제 통보 문맥) | 정보보호 담당 | 추정 |
| 네샤크라, 샤크라 | 샤크라(접근통제 솔루션) | 추정 |
| 오렌지 (데이터 작업 문맥) | ORANGE(DB 쿼리 도구) | 높음 (확인됨) |
| 오후 영업일 (적정성 평가 문맥) | 5영업일 | 높음 (확인됨) |
| 12, 시비, c2, 12사 (신용평가 문맥) | CB | 높음 |
| 가맹 데이터 (신세계·나이스 제공 문맥) | 가명 데이터 | 높음 (확인됨) |
| k3, k500, 펌프 | 원문 유지 | 모름 |
| 회원제 프로, 세 번째 프로 (DB 번호 발급 문맥) | 원문 유지 | 모름 |

**문맥에 따라 다른 대상**
- "나이스": CB(신용평가) 문맥이면 **나이스평가정보**, 가명결합·데이터 제공 중개 문맥이면 **나이스지니데이타**. 녹취 표기 "나이스진이", "나이스지니"는 나이스지니데이타.
- "팀장(님)": 별도 언급이 없으면 현 데이터사업팀 팀장 **이창재**. 과거 이야기에서 "강 팀장"은 전임 팀장 강상현.

**사람 이름**: 7-1 명단과 대조해 교정한다.

1. **이름 전체가 명단과 같으면** 그대로 쓴다.
2. **이름 일부(성 없이 이름만, "○○ 프로")가 명단의 한 사람과만 맞으면** 그 사람으로 교정한다. 예: "호철 프로" → 채호철.
3. **발음이 비슷한 이름**(한두 글자 차이)은 명단에서 후보가 **한 명뿐이고 문맥(담당 업무, 소속)이 맞을 때만** 교정한다. 교정 근거를 본문에 `(명단 대조: 원문 "정태원")`처럼 남긴다.
4. **후보가 두 명 이상**이거나 문맥이 안 맞으면 교정하지 않고 원문을 유지한 채 `[확인필요]`를 붙인다.
5. **명단에 없는 이름**은 타 부서·외부 인물 또는 전임자로 보고, 사람 페이지에 `소속: 확인필요`를 쓴다. 우리 팀원으로 단정하지 않는다.
6. 사람 페이지 **파일명은 명단의 정식 이름**(성 포함)으로 한다. 녹취 표기는 `aliases`에 모두 넣는다.
7. 새로 확인된 오인식 표기는 위 표의 "STT 오인식 사례" 칸에 추가하도록 보고한다.
8. 명단은 업무 연락 목적의 이름·직책만 담는다. 연락처·나이 등 개인정보는 넣지 않는다 (9장).

## 8. 숫자와 상충 처리

### 숫자
- 숫자는 **발언 그대로** 쓰고, **기준 시점**을 반드시 붙인다. (예: "2025년 목표 33억 원(회사 평가 기준)")
- 에이전트가 계산한 값은 `계산:`을 앞에 붙여 발언과 구분한다.
  예: "건당 100원 − 대행사 30원 = 매출 70원, − 통신비 26원 = 이익 44원 (계산: 발언 수치로 재구성)"
- 단위(원, 건, 명, %)와 기준(매출/이익, 연/월)을 빠뜨리지 않는다.

### 상충
같은 원본 안에서, 또는 원본 간에 내용이 다르면 **어느 한쪽을 지우지 않는다.** 아래처럼 표시하고 `확인필요.md`에 올린다.

```
> ⚠️ 상충: 2026년 목표 달성 기준이 40억 원(05:00)과 약 33억 원(07:53)으로 다르게 언급됨. (출처: 황성환)
```

## 9. 쓰지 않는 것

녹취에는 업무와 무관한 대화가 섞여 있다. 다음은 **위키에 옮기지 않는다.**

- 개인 신상: 나이, 출생연도, 정년, 가족, 휴가 계획, 건강
- 특정인에 대한 평가·감정·험담 (예: "○○ 팀장님이 싫어하신다")
- 욕설, 비속어, 잡담, 사적인 농담
- 다른 회사 구성원에 대한 사적인 이야기

단, 업무에 의미가 있는 부분은 **사실만 중립적으로** 남긴다.
- "휴가를 못 간다" → `리스크: 담당 업무의 대체자가 없음`
- "팀장님이 전결 틀리면 싫어하신다" → `규칙: 전결 오류는 결재 단계에서 엄격히 지적된다`

**민감 정보**: 개인 식별 정보(주민번호, 연락처 등), 계좌·비밀번호, DB 접속 정보는 원본에 있어도 위키에 옮기지 않는다.

## 10. 묻기(query) 규칙

1. 위키 페이지에서 먼저 답을 찾고, 근거 페이지를 `[[링크]]`로 밝힌다.
2. 위키에 없으면 "위키에 없음"이라고 먼저 말하고, 필요하면 `raw/`를 확인해 답한다.
3. 답변이 여러 페이지를 종합한 새로운 정리라면, 위키에 새 페이지로 저장할지 제안한다.
4. `초안` 페이지를 근거로 답할 때는 "검수 전 내용"임을 표시한다.
5. `stale_after`가 지난 페이지를 근거로 답할 때는 "재확인 필요"를 표시한다.

## 11. 점검(lint) 규칙

요청을 받으면 위키 전체를 점검하고 결과를 보고한다. 자동으로 고쳐도 되는 것과 보고만 할 것을 구분한다.

**자동 수정 가능**
- 끊어진 링크 (대상 페이지가 없음) → 페이지 생성이 필요하면 목록으로 보고, 오타면 수정
- 한쪽 방향만 걸린 링크 → 반대쪽 `## 관련`에 추가
- index.md에 빠진 페이지 → 추가
- 라벨 필수 필드 누락 → `확인필요`로 채움

**보고만 할 것 (사람이 판단)**
- 같은 대상으로 보이는 페이지 중복
- 상충 표시가 남아 있는 페이지
- `stale_after`가 지난 페이지
- 아무 곳에서도 링크되지 않는 고아 페이지
- 통제어휘 밖의 값
- 근거(`sources`)가 없는 사실

## 12. index.md와 log.md 형식

**index.md**
```yaml
---
title: 데이터사업팀 지식 위키
version: 0.1.0
entries:
  - 업무/LMS-광고.md
  - 프로세스/데이터-외부제공-전체-프로세스.md
  # ... 모든 페이지
---
```
본문에는 type별로 묶어 `[[링크]] — 한 줄 요약` 형식으로 나열한다.

**log.md** (최신이 위)
```
## 2026-09-28 ingest: raw/2026-09-28_서선화_데이터제공프로세스.txt
- 생성: [[...]], [[...]]
- 갱신: [[...]]
- 확인필요 추가: 3건
```

**확인필요.md**
```
- [ ] "경지"가 경영지원 부서가 맞는지 (출처: 서선화 05:12) → 물어볼 사람: [[서선화]]
- [ ] 2026년 LMS 목표 기준 40억 vs 33억 (출처: 황성환 05:00, 07:53)
```
해결되면 체크하고, 답을 해당 페이지에 반영한 뒤 `log.md`에 기록한다.

# 외부발송 용량과 파일분할

데이터를 외부로 보낼 때는 전송 방법과 파일 분할을 가·익명 시스템에 올리기 **전에** 정해야 한다.

## 규칙
외부 제공 데이터는 전송 가능 용량을 먼저 확인하고, 시스템 업로드 전에 필요한 만큼 파일을 나눠둔다.

## 이유
- 외부 문서 발송은 최대 4GB이며, 4GB도 전송이 원활하지 않다. (출처: 서선화 09:12)
- 반출 결재 때 파일 해시를 등록하고, 해시가 일치하는 파일만 나갈 수 있다. (출처: 서선화 17:59)
- 업로드 후에 파일을 다시 나누면 해시가 바뀌어 반출할 수 없다. (출처: 서선화 18:12)

## 어기면 생기는 일
시스템에서 앞 단계로 롤백해야 하고, 롤백 자체도 결재를 다시 받아야 한다. 과거 분할 압축을 여러 번 하다 실패해 고생한 사례가 있다. (출처: 서선화 09:16, 18:34)

## 구체적인 방법
- 용량이 크면 USB 반출, 분할 전송 등 방법을 먼저 결정한다.
- 결정한 방법에 맞춰 나눈 파일을 가·익명 시스템에 올린다.
